# Продуктивність ядра — 2026-11-01

Цей звіт описує оптимізацію v5. Подальша модель playground та її JSON-схема наведені в [Сценах playground](playground.uk.md).

Перший етап оптимізації зберігає контролер і правила сприйняття. Робоча гілка — `codex/scale-core`; нових залежностей немає. Наведені числа стосуються ядра, а не FPS зображення.

## Вимірювання

Для тривалого збору виграш менший: багато агентів зупиняються, а локальний пошук решти залишається витратним. Після 200 кроків обидві версії мають 886 завислих, 114 рухомих та нуль вибулих агентів. Це не гарантія завершення будь-якого збору 1000 агентів.

Відбитки положень, швидкостей, прискорень і станів збігаються з початковою версією в кожній парі запусків: відповідно `7d6ea305a929cb3d`, `fe4300a19b4cad0d`, `bc14a687214983d6`, `0d834223d0c95d7b`. Це перевірка регресій у цьому числовому середовищі, а не міжплатформний контракт. Початкові вимірювання: [CSV](benchmarks-2026-11-01.csv).

Початкова debug-збірка без оптимізації витрачала близько 253 мс на крок у перших п'яти кроках щільного перельоту. Тепер `[profile.dev] opt-level = 2` оптимізує й звичайний запуск з IDE/Cargo. Для порівнянь слід використовувати release.

## Зміни

- Просторова сітка знаходить видимих сусідів один раз для кожного рухомого агента на кроці. Індекси впорядковані, тому зберігаються порядок обчислень та розв'язання рівностей. Точні перевірки відстаней лишилися; кількість сусідів не обрізається.
- Для контактів є окремий просторовий відбір із запасом повного руху `2 * body_radius + 2 * speed * dt`. Додаткові комірки покривають округлення на включених межах. Точний хронологічний розрахунок збережено, зокрема для агентів поза взаємним оглядом. За крайніх координат чи масштабів використовується повний перебір.
- Пошук місця спочатку перевіряє нижню межу вартості й лише потім зайнятість та шлях повз припаркованих сусідів. Вільний доступний центр Gather уже є мінімумом, тому перевіряти навколишні точки не потрібно. Зсуви точок кільця обчислюються один раз на пошук.
- Прогноз швидкості пропускається, коли її базова вартість уже не може перемогти: штраф уникнення невід'ємний. Привід, набір напрямків та горизонт прогнозу збережено.
- Перегляд виконує максимум вісім кроків за кадр і повертає керування між кроками після восьми мілісекунд роботи. Один крок може тривати довше за цей бюджет. Накопичений модельний час зберігається; індикатор **Lag** показує відставання. За постійного перевантаження модель відстає від реального часу.

## Модулі

Таблиця описує структуру на етапі v5. Поточний поділ ядра, CLI та переглядача наведено в [карті коду](architecture.uk.md).

| Файл | Призначення |
| --- | --- |
| `src/simulation.rs` | Публічні типи, перевірка даних, початковий стан, команди, атомарний крок і базові Boids |
| `src/simulation/copter.rs` | Вибір місця, швидкості та привід з обмеженням jerk |
| `src/simulation/collision.rs` | Відбір можливих контактів і хронологічне виконання подій |
| `src/simulation/spatial.rs` | Просторові комірки та детермінований пошук сусідів |
| `src/simulation/math.rs` | Спільні векторні операції |
| `src/playback.rs` | Інтерполяція зображення та обмеження наздоганяння часу |
| `examples/benchmark.rs` | Повторювані вимірювання ядра й відбитки стану |

На цьому етапі оптимізації публічні імпорти та формат CLI `boids-2d-v5` залишилися незмінними. Сцени з’явилися у v6; широкий коридор використовує `boids-2d-v7`.

## Повторення

Компілюйте один раз, потім запускайте виконуваний файл:

```powershell
cargo build --release --example benchmark --locked --offline
.\target\release\examples\benchmark.exe 1000 20 3 gather
.\target\release\examples\benchmark.exe 1000 20 30 gather
.\target\release\examples\benchmark.exe 5000 20 30 gather
.\target\release\examples\benchmark.exe 1000 200 3 cluster
```

Повторіть тричі для кожного входу. Також підтримуються `flock` і `hold`. Некоректні входи та помилки ядра завершують вимірювання з помилкою; ініціалізація вимірюється окремо. Початковий код і виконуваний файл локально збережені в ігнорованій теці `work/optimization`; для поточних вимірювань ці чернетки не потрібні.

```powershell
cargo test --all-features --locked --offline
cargo clippy --all-targets --all-features --locked --offline -- -D warnings
cargo fmt --check
cargo run --release --features viewer --bin viewer
```

## Обмеження

Під час вимірювань v5 діяв ліміт переглядача 1000; згодом його прибрано. 5000 агентів перевірено лише без вікна. Радіус появи змінює щільність і поведінку, тому розріджені та щільні сценарії наведено окремо. Вимірювання не визначають FPS, пікову пам'ять, максимальну кількість агентів чи найгіршу затримку.

Ініціалізація досі перевіряє розміщення попарно. Коли всі бачать усіх, сітка не прибирає справжніх взаємодій: локальний пошук може потребувати `O(N * k²)` для `k` видимих сусідів, аж до кубічної складності у повністю щільному рої. Зіткнення, затори контролера та невдалі параметри залишаються можливими. Фізика й зображення працюють в одному потоці; за постійного перевантаження наступним кроком може бути окремий потік симуляції після профілювання конкретного сценарію. GPU, потоки, обрізання сусідів та наближене уникнення не додавалися.
